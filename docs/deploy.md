# Deploying to free hosting (no card)

"Free" here means no credit card or payment method is ever linked, not even for a verification
hold. The app is one container (`Dockerfile`: node build, `python:3.12-slim`, Debian's Stockfish,
about 490 MB). It needs a port from the host (`PORT`, read at start), CPU for the engine, and a
database that survives restarts: the free hosts wipe the disk, so set `TURSO_DATABASE_URL` and
`TURSO_AUTH_TOKEN` (Turso's free plan needs no card). The coach streams answers as server-sent
events, so the host's proxy must pass a long, chunked response through.

## Render, step by step

1. **Turso:** sign up at turso.tech (GitHub works), create a database `chess-coach`, copy its
   `libsql://` URL and create a database token.
2. **Render:** sign up at render.com with GitHub. If any screen asks for a card, stop and use
   SnapDeploy instead.
3. New, then Blueprint, then pick this repository and the branch to deploy. Render reads
   `render.yaml`: one free web service built from the `Dockerfile`, health check `/api/health`,
   `SECRET_KEY` generated by Render.
4. Fill in the values marked `sync: false`: `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, and
   `PUBLIC_URL` (`https://<service>.onrender.com`, used in password-reset links). Leave
   `GOOGLE_CLIENT_ID` empty unless Google sign-in is set up for that address.
5. Every push to the deployed branch redeploys.

## SnapDeploy, the fallback

Sign up, create a container from this repository's `Dockerfile`, set the port to `8765`, and add
the same environment variables plus `ENGINE_THREADS=1`, `ENGINE_HASH_MB=32`, `ENGINE_PROCESSES=1`
and `FORWARDED_ALLOW_IPS=*`.

## Honest limits

- **Cold start:** after 15 idle minutes the next visitor waits about a minute.
- **Slow engine:** a fraction of one CPU; the numbers are in the next section.
- **Monthly caps:** using up Render's hours or egress suspends the site until the next month; it is
  never billed.
- **Restarts:** a review running in memory is lost when the host restarts the service; the player
  starts it again.

## Measured under Render's free limits

The production image run locally with `docker run --cpus 0.1 --memory 512m`, `ENGINE_PROCESSES=1`,
`ENGINE_HASH_MB=32` (2026-10-25). Two engines instead of one used 462 MB and took 188 s to open
the port, because each Stockfish holds about 270 MB with its network and the opening book was
parsed before the port opened; both were changed.

| What | Time or size |
|---|---|
| Image | 496 MB |
| Container start to healthy (port open, engine up) | 41 s |
| Content warm in the background (book, courses, puzzles, plans) | 107 s after start |
| Memory after a full review | 269 MB of 512 |
| Bot reply, first move of a game (Pip 250 / Mei 1400 / Ivy 1800) | 1.6 s / 9.8 s / 16.6 s |
| Bot reply, later moves | about 1 s |
| Quick review of a 30-ply game | 133 s |
| Full review of the same game | 343 s |
| Maia-3 bot reply (a ladder bot after the book), idle, 2026-10-28 | median 0.5 s, p95 0.6 s (Sam, then on Maia, Ivy, Elena; 55 replies) |
| Maia-3 bot reply while a full review runs, 2026-10-28 | median 1.1 s, max 1.8 s (Sam; 8 replies); a Stockfish book reply waited 13-20 s for the one engine |
| Memory peak with Maia-3 loaded, through a full review, 2026-10-28 | 442 MiB (464 MB) of 512 MB, measured twice: 400 and 442 MiB |
| Content warm including the Maia-3 model, 2026-10-28 | 209 s after start (the host was busy with other runs) |

The first reply of each game took longer than the later ones; the cause was not measured. A wake
from sleep adds Render's own start of about a minute.
